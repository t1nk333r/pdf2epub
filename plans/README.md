### Finding 1 in detail

`pause_job` accepts a request while the state is `processing`, and the job
stays `processing` from the last committed page through margin stripping, the
full quality-report write, and the integrity checks — until
`_update("Building EPUB", …)` flips it. A pause landing in that window drives
`pause_requested → building`, which `_JOB_TRANSITIONS` forbids;
`require_transition` raises, the worker's catch-all marks the job `failed`, and
`failed` has no outgoing transitions while `resume_job` accepts only `paused`
and `interrupted`. Every page checkpoint survives but is unreachable from the
UI. On a job resumed after a publication failure the exposure is wider still:
all pages are already committed, so the analyzer's loop body never runs and the
cooperative pause check is never reached during the entire EPUB rebuild.

### Direction findings (not defects)

- **Retention and quota for the data root.** The README already states there is
  no cleanup, quota, or retention policy, and `jobs` holds every recovered job
  in memory with up to 2,000 log entries each. The checkpoint store makes
  per-job age and size trivially computable. Any automatic deletion of a
  converted book needs a confirmation model, so this wants a design plan before
  a build plan.
- **Measure the Latin-letter fallback's real cost.** `ocr.py:379` re-runs a page
  on the 32B model whenever the output contains any Latin character. Arabic
  books routinely carry ISBNs, foreign names, and page furniture, so this may
  double GPU time on a large share of pages. The rule is deliberate and
  test-pinned; the open question is the hit rate on a real book, which nobody
  has measured.

## Findings considered and rejected

- Unauthenticated settings API and no application auth: explicitly documented
  trade-offs in the README ("keep the application bound to localhost"), not
  findings.
- Mistral receiving full-resolution page images while the Ollama and
  OpenAI-compatible adapters downscale to 1280 px (`ocr.py:478` vs `ocr.py:388`,
  `ocr.py:429`): plausibly correct for a dedicated document-OCR service rather
  than a token-billed vision model. LOW confidence, no change recommended
  without a measurement.
- `fsync` on a read-only file descriptor in `CheckpointStore.write_page`: works
  on Linux and is harmless; noise.
- Quarantined `.corrupt-page-*.json` files are never cleaned up: trivial, and
  folds into the retention direction finding above.
- Treating missing EPUBCheck as a failed liveness check was rejected: it would
  invite container restart loops even though the web application can still
  provide diagnostics and setup guidance.
- Globally disabling uploads when Tesseract Arabic data is missing was rejected:
  Ollama or another ready provider can perform OCR, and embedded-text pages do
  not require Tesseract.
- Warning for every unconfigured hosted provider was rejected: those providers
  are optional and such warnings would be noisy rather than actionable.
- An in-memory-only pause button was rejected: it would not survive power loss
  or application restart and would give a false sense that hours of OCR were
  protected.
- Immediate cancellation of an in-flight Ollama request was rejected: page-end
  cooperative pause has clear durability semantics and does not discard an
  ambiguous partial model response.
- Automatic resume after reboot was rejected: long GPU work should restart only
  after explicit operator confirmation and readiness validation.

|---|---|---|---|
| `first20.pdf` (front matter of one book) | 20 | 1 (page 5) | 1 |

That is below threshold, but the sample is **underpowered and unrepresentative**,
not conclusive. Twenty pages of cover, dedication, colophon and contents is the

text is where such quotations cluster. Extrapolating from front matter would be
the wrong inference in either direction.

**Status: BLOCKED, not REJECTED.** The distinction matters — REJECTED would
claim the measurement was taken and the feature judged not worth building. It
was not taken. Nothing was implemented.

**To unblock**: run the Step 0 counting script over a real 100+ page Arabic
book, then either proceed or mark the plan REJECTED with the measured numbers.
The script is inlined in the plan and needs only a PDF; it does not require a
conversion, since it counts `﴿…﴾` markers in the extracted text directly. Note
that a fully scanned book has no embedded text layer and will undercount — for
those, run the count against a completed conversion's `quality-report.json`
instead, as the plan originally specified.

## Plan 12 — 2026-09-01

Written by a Fable subagent, executed by Sonnet, reviewed and merged.
Suite: **140 passing**, ruff clean.

Origin: an operator-reported miss. On page 15 of a real conversion the embedded
layer held `للتخندق` (correct) while the selected OCR read had `للخندق` — a
different word. The correct reading was in the candidate that lost.

`ocr_covers_embedded` cannot catch this and is not meant to: it is a bulk-loss
gate (length ratio + 50% word overlap). A one-character drop is invisible to it.

Measured before planning, on a real 20-page conversion:

- 32 dropped-character candidates across 10 comparable pages — **3.2 per page**.
- True positives include `للتخندق→للخندق`, `النصوص→الصوص` (texts→thieves),
  `التنوع→النوع` (diversity→type), `يخاطب→يخطب` (addresses→preaches).
- **Precision ~50%** — tanween-alef variants (`سلفا→سلف`) are indistinguishable
  from real drops. Hence: review hint, never a correction.
- A plain word diff does **not** work: 30+ items per page, drowned in the
  embedded layer's own mid-word ligature damage. The one-character constraint
  is what makes the signal usable.

Three invariants held and verified on the merged tree: the text is never
modified, `integrity` is built solely from `PageSelection` so a hint cannot
block publication, and `ocr_covers_embedded` / `choose_ocr` are byte-identical.

**This plan was the best-specified of the session, and the difference was
method**: its author ran every verification command before writing it down. Its
Step 2 probe was confirmed to return `[('للتخندق', 'للخندق')]` against a real
implementation before an executor ever saw it, and its `-k` filter was checked
to match the tests it specifies. The one defect found was drift, not error —
15 stale test counts after an unrelated commit shifted the baseline 132→133.

One test deliberately pins a known false positive (`سلفا→سلف`) rather than
